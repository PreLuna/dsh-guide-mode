# Phase 5：独立管理器入口与多包安装管理

更新：2026-11-08（Asia/Shanghai）。方向已由用户确认；5A/5B/5C 本地包首版已验收，后续按 5D → 5E 推进。Phase 1–4 的 2026-11-05 验收记录保持历史事实；实际交付进展统一记录在 [项目状态](../PROJECT-STATUS.md)。

## 1. 已定方向

用户先安装 `guide-manager`，从官方插件页的「指导」管理页安装推荐组件或选择可选组件，随后逐组件管理、升级和修复。保留六个独立运行包及独立 manager，不新增 suite 作为强制依赖入口，不合并运行代码。

`guide-manager` 是安装入口；`guide-panel` 是依赖 preset/admission/shield 的业务面板，不能承担首次安装。manager 不导入运行组件，也不通过 dependencies/peerDependencies 强制安装全部组件。组件分别作为当前 profile 的直接依赖与 bundle 登记，避免 suite 的间接依赖与独立升级产生两份版本。

此前“尚无实际安装痛点、暂缓 suite”的判断已被用户反馈取代。单安装入口与单 npm 代码包是不同目标；本阶段选择前者。

## 2. 使用流程与版本策略

1. 安装 manager，其他六个包均未安装时仍可打开管理页，显示缺失组件与安装入口。
2. “安装推荐组合”安装六组件；单独选择 panel 时自动补齐 preset、shield、admission，admission 自动补齐 shield。可选 sidebar/goal 单独选择，宿主与外部依赖另行检查。
3. 展示具体包名、精确版本、联动组件和是否需要重启；用户确认的是这份计划。执行前重新核对安装状态，过期计划必须重新预览。
4. 默认使用经过验收的版本组合；单组件升级也检查契约、组件依赖、DSH 构建与上游产物。独立升级不表示任意版本混用，也不表示热更新。
5. 本机 link 开发与 registry/tarball 分发分别识别，不用安装动作隐式覆盖已有 link，不把当前未发布的 `@local` 包伪称为可从 registry 安装。

发布目录包含组件、精确版本、来源、契约与依赖。首版可用本机生成的 tarball 目录验证，不在本阶段擅自公开仓库、发布 npm、选择正式命名空间或许可证。后续远端目录独立于 manager 发版维护，校验来源与格式，不能让浏览器请求任意包安装。

## 3. 技术事实与边界

本机 DSH `0.2.1-rc.3` 官方实现经只读检查：

- `pluginManager.installBundle(spec, options)` 支持 `enabled:false`、`saveExact:true`、request id、取消与安装状态事件；底层使用宿主 pnpm。
- 存在 HMR 时安装已登记同名依赖可能返回 `already-installed`；运行中卸载可能返回 `stop-profile`。不能把重复 install 或 remove/install 当成可靠升级事务。
- `enabled:false` 只表示不选中新 bundle，不是完整的离线暂存/隔离安装；安装仍会修改依赖图。已有 bundle 的启用状态也不能据此推定已清除。
- 单次安装的官方失败恢复不等于多个组件的组合原子性。需要保存每步结果，停止后可重试，并在不完整时避免激活业务组件。
- 原 rollback helper 仅恢复冷切换 patch；不是包版本回滚。不得把它显示为 Phase 5 包版本恢复。

包操作复用官方服务或其共享 `runProfilePnpm` 与 `withFileLock`；manager 负责白名单、依赖计划、状态与结果。5A 选择独立停机执行器，避免在运行期间触发核心更新。不能另起 npm 在使用 pnpm 的 live profile 中改依赖，也不能与官方插件页并发无锁写同一 profile。

## 4. 实施顺序

### 5A：管理器安装入口

- manager-only 启动与缺失组件展示；可信发布目录；推荐组合和依赖补齐计划。
- 先做首次安装，已有组件不替换；精确版本、计划指纹、执行前复核。
- 安装与激活分开；首次安装先不选中 bundle，全部成功后再进入冷激活步骤；goal adapter 与原 driver 保持互斥。
- 安装过程和结果落盘；中途失败保留每步事实，重试重新计算；不能把“已下载”显示为“运行就绪”。
- 管理页提供进度、失败原因、重试、重启生效说明；隔离 profile 与本地 tarball 验证。

### 5B：独立升级与包版本恢复

- 推荐/自定义版本组合、兼容范围与验收矩阵；放开硬编码统一版本的工程检查，保留实际契约约束。
- 可预检的升级计划、旧版本产物与依赖锁/配置备份、停机执行器、恢复旧依赖图与旧包、重启后的版本与健康核对。
- 处理跨版本配置/数据迁移，不能承诺仅恢复 manifest 就能逆转有副作用的迁移。
- 多组件操作与官方插件页共用写入约束；刷新/断线后恢复任务结果。

### 5C：卸载、修复与管理器升级

- 按依赖拒绝不完整卸载；卸载 goal 恢复原 driver；preset 涉及已有会话恢复，保留保护。
- manager 增加可信本地发布目录自升级，由复制到 profile 自有目录的独立 helper 执行；升级前给出外部恢复入口，新版本面板不可用时仍能恢复。registry 来源继续由官方插件页维护。
- `guide` skill、skills manager、better-sidebar 为外部依赖，单独显示与处理，不把六包安装完成当成全部能力就绪。

### 5D：远端分发、查询与下载

- 2026-11-08 用户同意优先接通现有 GitHub 仓库 Releases：固定提交产物、远端版本/兼容清单、私有鉴权与下载准备，再复用现有本地安装/升级/恢复。
- 查询元数据与包下载分开；按所选依赖/兼容闭包准备，全部校验后才形成可确认的本地执行计划。
- 首版沿用私有仓库策略，不以公开仓库或 npm publish 为前提。5D-0～3 发布格式、发布端、消费后端及 HTTP/UI 已本地实现，见 [格式与工具](PHASE-5D-RELEASE-FORMAT.md) / [管理页](PHASE-5D-HTTP-UI.md)；真实远端整体验收待 5D-4，完成后再开始 5E。

### 5E：当前 link 来源一次性迁移

- 只迁移已安装的七个自有包中的 link 来源，不借迁移补装缺失组件或隐式替换 registry/git 来源。
- 比较实际源码内容、备份源码快照和 profile 文件；独立助手停机切换来源，保留启停、数据和外部插件，失败可从面板外恢复。
- 5D/5E 详细施工顺序、拟修改位置、逐项验收和阶段门禁见 [施工方案](PHASE-5D-5E-IMPLEMENTATION-PLAN.md)。5D-0～3 已本地施工；真实发布、5D-4 整体验收与 5E/live 迁移尚未执行。

## 5. 验收与交付纪律

5A 至少验证：manager-only 页面；推荐组合/单组件依赖补齐；包白名单与失效计划拒绝；中途失败与重试；重启前不启用不完整组合；goal 原 driver 配对；刷新后可查询结果；打包不漏运行文件。

5B 增加：单组件升级实际加载目标版本、联动约束、失败后旧包与配置可恢复、重启健康检查、与官方操作冲突。5C 增加：组件缺失/损坏时 manager 仍可修复及卸载恢复。

先在隔离 profile 验证。实现、测试通过、真实宿主隔离验收、live 部署分别记录；未验证的环节不得写成已完成。此次授权包括文档与本地施工，不等于 npm 发布或替换 live desktop 的分发来源。
