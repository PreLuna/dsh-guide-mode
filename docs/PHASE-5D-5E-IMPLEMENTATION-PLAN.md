## 3. 5D-0：发布格式与规则

### 3.1 格式

保留本地 schema 1（安装）、2（组件升级）、3（manager 升级）。新增远端 schema 4 发布清单，建议附件名 `guide-release.json`，仅作为传输/版本发现层，不改变既有数据 schema。

远端清单至少包含：

- 产品标识、格式版本、发布 tag、来源提交 SHA。
- 七包白名单的 key/package/version，contract/dataSchema；manager 另含 controlSchema 和宿主要求。
- 每个 tgz 的固定附件名、SHA-256、字节数、所属发布引用；不含开发者绝对路径、临时签名 URL 或凭据。
- 安装推荐组合、有限兼容组合、内部依赖要求及声明的验收基线。
- 仍受支持的旧包引用，确保更新后能识别已安装版本及其升级路径；不假设最新 Release 的七个包可以覆盖所有历史组合。

附件发布后，客户端通过指定仓库/tag 与附件清单解析实际 release/asset ID，绑定本次查询快照。清单及产物必须来自配置的仓库与所选已发布 Release；HTTP 客户端只传版本/组件/任务标识，不传任意下载 URL、路径或 shell 命令。

### 3.2 版本与发布规则

1. 发布 tag 标识一组发布产物，七包各有自己的精确版本；独立升级不强制七包同时涨版本。
2. 已发布的同包同版本必须保持同一产物 SHA；源文件改变时必须发新包版本，不覆盖旧资产。仅重新压包产生不同字节也按冲突处理，优先复用原 tgz。
3. 默认查询已发布、非 prerelease 的稳定候选；“最新 Release”只用于发现候选，实际可安装版本还须符合宿主和兼容组合。
4. 发布清单可继续指向旧 Release 的固定产物。测试故障版只进入隔离夹具/明确测试发布，不进入默认稳定候选。
5. 一次准备绑定所选 release ID、清单哈希和包 SHA；期间出现新发布，不静默替换已经预览的版本。

### 3.3 连接与鉴权

Host 配置指定 owner/repo、稳定候选策略和凭据环境变量名；首版后端读取本机 `DSH_GUIDE_GITHUB_TOKEN`。配置和状态中只保存变量名与连接结果，不保存 token 内容。重启后凭据是否仍可读取须进入验收，不能依赖开发终端的临时环境恰好存在。

私有仓库使用该仓库 Contents 只读权限；公开资源可无需凭据。发布凭据与客户端只读下载凭据分开。浏览器不持有 token；token、Authorization 头及临时签名地址不进入日志、state、计划、launcher 或备份。

GitHub 附件下载可能返回文件或重定向；后端处理二者。凭据仅发给 GitHub API，不随跨域跳转转发；附件下载目标按官方 HTTPS 下载路径校验。明确区分未授权、无权限/找不到仓库、限流与网络超时，避免把鉴权 404 当成“没有新版本”。

验收：清单中无本机路径；七包、依赖和宿主字段可独立验证；非法元数据、重复包版本冲突、未知 schema/包名被拒绝；凭据不出现在任何持久产物中。

## 4. 5D-1：发布端施工

拟新增 `scripts/prepare-remote-release.mjs`，输出新目录下的七包/所需历史引用、远端清单、哈希清单和发布摘要。复用固定提交归档流程，从提交字节打包；开发夹具可使用明确标记的工作树模式，但不能被正式发布入口误用。

流程：固定已审阅提交 → 工程检查 → 打包与归档内容核对 → 编译兼容组合/远端清单 → 生成可审阅发布摘要 → 上传完整草稿产物 → 核对附件名称/数量/字节/hash → 将完整发布提供给稳定查询。

先实现本地生成及草稿上传工具；上传、正式发布作为独立可见动作，不由普通本地打包顺带触发。首批发布与远端真机验收使用具体可审阅的产物。现有未提交改动不自动视为正式发布提交；不阻止先开展本地代码和夹具验证。

拟新增 `.github/workflows/release.yml`，使用明确 tag/手动触发，复用现有 Windows 工程检查，发布 job 使用必要的 Contents 写权限；现有 `.github/workflows/test.yml` 保持只读。发布流程失败则不提供半成品稳定 Release。最初可先用同一发布工具手动完成流程，再接自动化，二者使用相同产物格式。

验收：从指定提交在独立目录重建产物；同版本不同字节冲突被拒；缺包/错误元数据不产生可用发布；普通 push/test 不上传或发布安装包。

## 5. 5D-2：查询、下载与本地目录适配

拟新增 `guide-manager/remote.js`（远端元数据/任务/目录适配）和 `guide-manager/github-source.js`（GitHub API、鉴权和下载传输）。HTTP 请求通过 Host 执行，使用内置网络能力，不要求用户另装 git/gh，也不依赖浏览器跨域请求。

下载准备流程：

1. 拉取并验证远端元数据，展示候选；这一步不下载全部 tgz，也不改变 profile 四文件。
2. 用户选择安装/升级/manager 目标后，共用现有依赖与兼容规则，计算本次需要的包。包括必要联动、实际验证及旧版本备份所需产物；不是只下载用户点中的一个包。
3. 有效 SHA 缓存直接复用；其余下载到临时文件，限制体积、超时和重试次数，支持取消并识别重启中断。首版取消后可重新下载，不要求 HTTP Range 断点续传。
4. 校验长度、SHA、tar 内容、实际包名/版本/契约/宿主字段。失败不提升为可用包，不停止 DSH。
5. 经缓存写锁与原子提交形成稳定缓存；不覆盖已验证的同 SHA 内容。下载与冷执行并发时不能读取半写入文件。
6. 为本次准备生成不可变本地目录快照，将来源映射到绝对缓存路径。完整元数据仍验证；只有本事务全部必需文件验证通过才允许生成正式计划。
7. 使用既有安装/升级/维护计划指纹预览和确认。准备后 profile 有变化，仍重新预览；冷执行器在官方 profile 锁内再次核对全部目标和旧包。

目录快照按内容哈希保存到 profile 自有 remote 子目录，不覆写已被 pending/事务引用的目录。未来离线恢复只依赖本地事务/缓存；源仓库或 token 暂时不可用不应阻断已有恢复。

任务落盘仅保存状态、进度、来源身份与清单哈希；刷新可恢复展示。检查更新与下载使用异步任务，不能把 GET state 变成阻塞的远程请求。未完成任务在 Host 重启后显示中断并可重试，不自动安装。

## 8. 5E-0：来源清点、差异与迁移计划

拟新增 `guide-manager/migration.js`。首版自动切换范围只含当前 profile 已安装、直接依赖为 `link:` 的七个自有包；manager 一并清点。已是稳定缓存来源的包保留，缺失组件不顺带安装。registry、git、workspace 或未知来源先明确拒绝迁移，不在本轮隐式扩展支持。

预检并展示：原 spec/源码真实路径、实际版本、源码随包文件清单和哈希、目标 Release/包 SHA、实际代码差异、原启停配置、宿主基线、四文件快照、待执行任务及恢复入口。

不能只比较版本号：当前 1.1.0 link 含未发布改动。先冻结所选源码，比较发布内容；若目标确实改变代码，页面必须标明“切换来源并更新代码”。首次迁移优先选择与审阅源码一致的发布基线，再独立验证后续版本升级。Host 内存代码与磁盘源码可能不一致，需记录源变更诊断；存在漂移时先冷重载核对，不把磁盘快照称为内存代码快照。

迁移计划绑定源码内容指纹、原 spec、已下载产物、四文件、loader 启停与独立控制器内容。确认前/停机执行前再次检查；源码编辑、目标变化、配置变化、其他 pending 或未恢复事务均拒绝过期计划。

## 9. 5E-1：独立停机切换与恢复

拟新增 `helper/apply-migration.mjs`、迁移/恢复入口及独立事务目录，复用 5C 控制器复制、目标进程定位、官方 profile 写锁和 pnpm。manager 也可能被替换，因此执行和恢复必须从 profile 自有控制器目录运行。

事务顺序：

1. 下载和校验全部目标；保存可执行计划，给出切换及外部恢复命令。
2. 停止指定实例，在官方锁内重新验证来源、源码、配置与目标。
3. 备份四文件、原 link 关系及真实路径/哈希、原配置启停状态，并将原自有包随包内容打包成可校验快照。快照仅包含白名单随包文件，不递归复制整个源码仓库、node_modules、会话或凭据。
4. 一次解析本次需切换的自有直接依赖，将其固定到 profile SHA 缓存；禁用脚本和自动 peer 安装。保留 bundle 与原有 patch、goal 配对以及全部无关依赖。
5. 校验实际包文件、name/version/contract、peer、宿主与组合配置，核对无关 manifest 字段、patch/workspace 及用户数据 sentinel；记录完成回执，再重启核对服务。
6. 普通失败恢复四文件和原依赖图；原源码路径及内容未变时恢复原 link。若原目录丢失/改变，使用自有代码快照恢复可运行旧内容，并明确记录实际恢复来源，不能伪称已恢复原 link 路径。
7. 恢复再次失败或中断时保持停止，保留证据和外部入口，不盲删 pending。成功切换不删除或改写开发源码目录。

原 link 恢复依赖原路径、冻结内容与 pnpm 图；这不是原包版本回滚的一次普通调用，需要独立事务类型与验证。所有准备/执行与 5A/5B/5C 互斥，刷新和断线后仍可查询结果。

## 10. 5E-2：UI 与迁移验收

管理页增加“切换到发布包”入口，列出实际需要切换的包、源目录、目标、差异和备份；必须确认具体计划，不复用首次安装来绕过现有 link 保护。源码无变化和存在代码更新的情况分开展示。迁移成功后显示当前来源为受管理包，普通升级区可继续工作。

| ID | 场景 | 必须满足的断言 |
|---|---|---|
| E-01 | 清点 | manager-only、七包 link、混合 link/缓存、缺失组件均正确；未知/registry 来源不被误换 |
| E-02 | 内容漂移 | 同版本不同内容可见；预览后源码/配置改动拒绝；不覆盖开发目录 |
| E-03 | 切换 | 仅替换选定已安装自有包来源；启停、goal 配对、其他插件和用户数据保留 |
| E-04 | 普通失败 | 真实 pnpm 操作/后置核对注入失败，恢复原四文件及原 link 关系，旧服务可运行 |
| E-05 | 外部恢复 | 新 manager 无法加载、远端断开、原源码目录缺失时，独立控制器/代码快照仍可恢复；来源变化记录真实 |
| E-06 | 后续更新 | 迁移后走远端单包升级、必要联动、修复及版本恢复，未重复触发来源迁移 |
| E-07 | 平台 | 真实 Edge、独立 Electron 桌面、官方写锁争用和限定实例进程保护通过；live 四文件在隔离测试期间不变 |

5E 隔离验收完成后，才形成针对当前 live 的具体来源切换计划和备份清单。方案和隔离代码施工不等于已切换 live；当前仍保留 link 部署事实。
